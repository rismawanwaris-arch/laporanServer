§1
Konteks

Konteks & tujuan

Setiap hari, operator di tiap outlet melayani tarik tunai: pelanggan transfer / gesek / bayar QRIS, operator memberi uang tunai. Otomax mencatat sisi “reseller”; bank mencatat sisi uang masuk. Keduanya harus ketemu.

Yang sering tidak sinkron: referensi transaksi ditulis beda antara bank dan Otomax; setoran dicatat generik (Auto Deposit BCA) tanpa nomor referensi; transaksi QRIS di-bulk ke Otomax keesokan harinya; dan sebagian transaksi salah label bank.

Tugas aplikasi ini satu: ambil data seharian, tunjukkan mana yang cocok dan mana yang perlu dicek — dengan mutasi bank sebagai kebenaran, bukan Otomax.

Pengguna: operator pusat yang menutup buku harian. Bukan akuntan, bukan developer. Alur harus tahan salah-input dan jujur soal apa yang belum beres.
§2
Fondasi

Prinsip desain

Mutasi bank = acuan
Setiap kredit di rekening adalah fakta. Otomax meng-counter mutasi bank, tidak sebaliknya. Semua angka dasbor dibingkai dari sisi bank: “uang masuk”, lalu “sudah / belum tercatat di Otomax”.
Parsing di peramban
Seluruh pembacaan file & pencocokan berjalan client-side. Server hanya menyimpan. Data mentah tidak meninggalkan peramban sampai pengguna menekan simpan.
Database = sumber kebenaran
Sejak revisi DB-first: simpan data mentah ke DB dulu, semua analisa dijalankan atas record, dan hasilnya ditulis balik. Dasbor membaca ringkasan dari DB.
Degradasi anggun
Tanpa server (dibuka sebagai artifact / file lokal) aplikasi tetap jalan penuh — tombol jadi “Analisa data”, analisa langsung dari kotak, tanpa riwayat.
Satu tanggal, satu record
Impor multi-hari otomatis dipisah per tanggal usaha. Tiap record menganalisa baris Otomax & mutasi bank tanggalnya sendiri.
Jujur soal ketidakpastian
Yang tidak bisa dicocokkan sistem tidak disembunyikan — masuk kolom “perlu dicek” / tab “Perlu perhatian”, lengkap dengan tombol audit manual untuk keputusan pengguna.
§3
Arsitektur

Arsitektur sistem

Tiga bagian: peramban (semua logika), server Express tipis (hanya REST + berkas statis), dan satu file SQLite. Otentikasi opsional — satu password bersama, aktif hanya bila di-set.

  • Front-end — satu file public/index.html: HTML + CSS + JS inline, tanpa framework/bundler. fflate (dari jsDelivr) untuk membaca .xlsx di peramban. Halaman /kelola terpisah untuk manajemen DB.
  • Server — server.js (Express 4) + db.js. Tanpa ORM. SQLite lewat modul bawaan node:sqlite — tidak perlu native build, file DB kompatibel DB Browser.
  • Auth — satu password bersama; token sesi disimpan di memori server (hilang saat restart — cukup untuk jaringan rumah). Password tersimpan di DB menang atas env APP_PASSWORD.
  • Shutdown — SIGINT/SIGTERM → PRAGMA wal_checkpoint(TRUNCATE) + close, supaya file rekap.db aman dibuka DB Browser.
§4
Alur

Alur data

Sejak revisi DB-first, menyimpan dan menganalisa dipisah. “Simpan ke database” hanya menulis data mentah; rekonsiliasi dijalankan dari daftar record.

  1. Impor — pengguna menempel / membuka 5 file, isi catatan opsional, tekan Simpan ke database.
  2. Deteksi tanggal — Otomax di-parse, dikelompokkan per tanggal usaha. Multi-tanggal → panel pilihan: Pisah per tanggal (default) atau Gabung jadi 1 data.
  3. Simpan — tiap record menyimpan seluruh teks mentah + ringkasan ringan (kategori & total per tanggal; belum ada pencocokan bank). Tanggal sama = ganti.
  4. Analisa — dari daftar / dasbor. Ambil record, jalankan rekonsiliasi penuh, PATCH ringkasan lengkap balik ke record.
  5. Tinjau — dasbor (per tanggal) atau tab Rekonsiliasi (detail per bank). Ubah sandingan / keputusan audit → Simpan hasil mem-PATCH record yang sama.

§6
Inti

Mesin rekonsiliasi

Per bank: kredit di mutasi rekening jadi tulang punggung. Baris Otomax berlabel TARTUN / BAYAR KE <BANK> dicocokkan ke kredit lewat serangkaian pass yang makin longgar. Sisa di kedua sisi masuk tabel audit manual.

Kosakata status
StatusArti
cocokreferensi + nominal persis
cocok_fuzzynominal sama, referensi diformat ulang (BCA/Mandiri) — cocok via token / substring
cocok_depositsetoran generik (“Auto Deposit BCA”) disandingkan per nominal unik atau kode outlet
cocok_manualpengguna menekan “Cocok” di tabel audit
salah_bankOtomax melabeli bank keliru; bank sebenarnya teridentifikasi di pass lintas-bank

tidak_adatak ada pasangan. Sisi bank: “belum tercatat di Otomax”. Sisi Otomax: “tanpa bukti mutasi”
QRIS / BCA-Merchant

Baris Otomax TARTUN QR BULK disandingkan ke agregat merchant (per Merchant ID) dengan prioritas: sandingan tersimpan (rt-qris-map) → nama outlet persis → nominal unik → nama mirip & tunggal. Nama merchant beda dari nama outlet Otomax (mis. ALFA 1 CELL vs PLC ALFA1 PASIR IMPUN) — sisa disandingkan manual lewat <select>, disimpan per Merchant ID.

Konsolidasi nama outlet

Mutasi BCA menyebut kode (… Tartun PLC68 …); Otomax mencatat deposit-nya hanya dengan nama di kolom reseller (PLC DM). Peta ID agen → nama outlet (rt-outlet-map, seed 44 outlet, dapat ditempel-ganti di Pengaturan) menyatukan keduanya di pass deposit & di tabel audit.

§7
Aturan

Derivasi tanggal usaha

Jam entri Otomax bukan tanggal transaksi. Baris QR bulk & admin dientri keesokan harinya tapi keterangannya memuat tanggal aslinya.

tanggalUsaha(r) untuk tiap baris:

  1. Cari TGL DD-BLN-YYYY di keterangan (mis. TARTUN QR BULK TGL 31-AGS-2026). Ketemu → itu tanggalnya.
  2. Tidak ketemu → pakai tanggal dari timestamp baris.

Peta bulan menerima ejaan Indonesia & Inggris: JAN FEB MAR APR MEI/MAY JUN JUL AGU/AGS/AUG SEP OKT/OCT NOV/NOP DES/DEC. tanggalDataOtomatis(rows) = modus dari semua tanggal usaha → jadi tanggal record saat “gabung”; saat “pisah”, tiap tanggal unik jadi record sendiri.

Contoh nyata: satu ekspor OTOMAX.xlsx terbaca sebagai 46 baris → 31 Agu, 45 → 1 Sep, 553 → 2 Sep — meski semuanya dientri sekitar 2 Sep.
§8
UI

Halaman & navigasi

Satu halaman, menu bar di header: Dashboard · Import Data · Rekonsiliasi · Pengaturan + pemilih tanggal + toggle tema. Menu Dashboard tampil hanya bila ada server + login.

Dashboard
Halaman pertama. Tabel 7 hari (di-anchor ke data terbaru): Tanggal · Uang masuk (bank) · Otomax · Selisih · Perlu dicek + baris total. Tombol “Analisa N hari” menghitung semua record yang belum dianalisa; klik baris → analisa lengkap.
Import Data
5 kotak (Otomax + BRI/BCA/Mandiri/QRIS), tombol 📁 buka file per kotak, Simpan ke database, panel pisah/gabung untuk multi-tanggal. Di bawah: daftar Data tersimpan — tiap record punya tombol Analisa / Hapus.
Rekonsiliasi
Kartu angka + tab: Perlu perhatian (default) · Ringkasan · Rekonsiliasi (sub-nav per bank + tabel audit) · Kategori (termasuk rekap per tanggal) · Per outlet. Banner “fokus tanggal” untuk record hasil pisah. Tombol Simpan hasil mem-PATCH record.
Pengaturan
Tema (terang/gelap/sistem) · sandingan merchant↔outlet · konsolidasi nama outlet · keputusan audit manual · akun (login / ganti password) · link Kelola DB · hapus data lokal.
/kelola
Halaman terpisah: tabel semua snapshot, edit tanggal/catatan inline, lihat teks mentah, hapus satu / semua, info ukuran DB.
Desain informasi dasbor: selisih ≠ 0 dan “perlu dicek” > 0 dirender merah (semantik, bukan aksen). Hari tanpa data tampil redup. Ini alat yang dipindai, bukan dokumen yang dibaca.

§12
Rasional

Keputusan & trade-off

Parsing client-side
+ privasi, nol beban CPU server, jalan sebagai artifact offline.  − mesin terduplikasi di 4 tempat.
node:sqlite bawaan
+ tanpa native build, satu file, kompatibel DB Browser.  − wajib Node ≥ 22.5.
Sesi di memori
+ sederhana, cukup untuk LAN rumah.  − logout saat server restart.
DB-first (simpan → analisa)
+ DB jadi sumber kebenaran, dasbor cepat baca ringkasan, data mentah aman lebih dulu.  − analisa perlu satu klik; re-analisa menulis balik.
Bingkai bank-first
+ sesuai realita (uang bank = fakta), mengarahkan perhatian ke selisih.  − semua label UI harus konsisten “dari sisi bank”.
Pisah-per-tanggal default
+ tiap hari jadi record mandiri, dasbor bersih.  − lag QR bulk yang melintasi batas tanggal tidak terekonsiliasi — pakai “gabung”.
Audit & outlet-map di localStorage
+ tanpa skema tambahan, instan.  − per-peramban, tidak lintas perangkat.
§13
Backlog

Hal terbuka

  • Settlement BCA-Merchant (format tanpa tanggal) tidak bisa disaring per tanggal untuk record hasil “pisah”.
  • Keputusan audit & peta outlet per-peramban — kandidat pindah ke DB (settings atau tabel baru) supaya lintas perangkat.
  • Alur “pisah” menyimpan blob mentah utuh di tiap record lalu menyaring saat analisa — belum ada upload mutasi bank per-tanggal.
  • 4 salinan mesin rekonsiliasi harus disamakan manual setiap kali aturan berubah.
  • Tanpa undo per-baris untuk “Cocok” yang sudah dikonfirmasi (hanya reset menyeluruh / tombol “Bukan”).
